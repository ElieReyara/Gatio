## Micro-plan
1. `packages/shared` : format du QR (version, clé, billet, événement, catégorie = 50 octets + signature 64, base64url), sans dépendance, utilisable dans le navigateur ; tests.
2. API : signature Ed25519 avec le module `crypto` de Node (clé privée en variable d'environnement, script de génération, clé éphémère en développement si absente, obligatoire en production) ; tests.
3. API, prototype (développement seulement, jetable en tranche 10) : liste fictive en mémoire (événement, catégories Standard et VIP, billets valides, utilisé, annulé) + création d'un billet après téléchargement ; routes `/api/v1/dev/scan-prototype/*`.
4. Web : relais `/api/v1/*` vers l'API (le téléphone ne voit que le site, par le tunnel).
5. Web : vérification locale (signature, événement, liste, passages locaux) en fonction pure testée, y compris contre une signature produite par Node.
6. Web : page `/scan` selon C2 (caméra, indicateur, résultats plein écran avec icône, mot, son et vibration, retour d'un toucher ou après environ 1 s), IndexedDB (liste, passages), service worker et manifeste (installable, hors ligne), mesure `verifyMs`.
7. Web : page d'essai `/dev/billets-essai` (développement seulement, sur l'ordinateur) qui affiche les QR fictifs (valide, utilisé, annulé, autre événement, signature fausse) et crée un billet après téléchargement.
8. `pnpm verify`, revue isolée, essai sur téléphone par le responsable (PC-1).

## Décisions prises seul (option simple et réversible)
- Liste fictive en mémoire de l'API (pas de table : billets, commandes et événements viennent aux tranches 3 à 6) ; identifiants fixes pour survivre à un redémarrage.

- « Déjà utilisé » : détail « Premier passage à … » seulement quand ce téléphone a fait le premier passage (l'heure n'est pas dans le manifeste du contrat, écart E6 en attente).
- Temps de vérification : affiché discrètement dans l'indicateur, en prototype seulement (aucune maquette ne le montre ; il servira aux mesures de la tranche 10).
- La page de scan est essayée en mode production (`next build` puis `next start`) : le service worker n'est pas fiable avec le serveur de développement.
